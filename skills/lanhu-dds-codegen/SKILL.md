# 蓝湖 DDS 代码还原

DDS（转代码）是蓝湖提供的结构化布局树。插件把它编译成每屏一份规格表 `screen-N.spec.md`（1.3–12KB：层级、屏内坐标、间距、样式、切图清单、文案）和一张裁图 `screen-N.png`，照这两样写代码。全程只用三个工具：`lanhu_dds_doctor`、`lanhu_dds_screens`、`lanhu_dds_build`。

## 流程

1. `lanhu_dds_doctor({})`：确认项目规范、输出单位、UI 库清单就绪（§2）。
2. `lanhu_dds_screens({ url })`：拿到每屏文案与同页分组，对照旧页面找出「旧页有、设计稿没画」的功能（§3）。
3. `ask_user_question` 问一次：模式、页面文件 → 屏号、旧功能去留（§3）。
4. `lanhu_dds_build({ url, plan })`：把用户的回答填进 `plan` 编译（§4）。
5. 按返回的 `work` 逐个文件做：读这一个文件名下的规格表与裁图 → 写代码 → 对它跑格式化与 lint → 再读下一个文件的（§5、§6）。
6. 全部文件通过后跑一次 `lanhu_dds_doctor({})`，按返回的 `closeout` 逐项确认一次，交付（§7）。

## 1. Cookie

唯一存放处是 `~/.dsh-lanhu-dds/cookie`（0600）。文件在就自动复用，不用问用户。

- 工具返回 `missing-cookie`：把返回里的 `say` 和 `howToGet` 转述给用户，停下等。
- 用户贴回 Cookie：传给 `lanhu_dds_screens` 的 `cookie` 参数，工具真读一次设计图，通过才落盘。
- 返回 `cookie-expired`：请用户换一份。清除旧值用 `lanhu_dds_doctor({ forget: true })`。

Cookie 等同登录态：不写进代码、不提交、不在回复里回显。

## 2. 项目规范与 UI 库

`lanhu_dds_doctor({})` 自动定位当前工作目录，返回：

- `unit`：输出单位（`designWidth` 750 → `design`，375 → `css`）。
- `rules`：项目已有 `AGENTS.md` / `CLAUDE.md` 时以它为准（`delegatedTo`）；两者都没有再跑 `lanhu_dds_doctor({ init: true, ui: true })` 生成模板并按仓库现状补齐。
- `ui`：`present: false` 时跑 `lanhu_dds_doctor({ ui: true })` 生成 `.agents/skills/lanhu-dds-codegen/ui-library.md`（组件、props、插槽、CSS 变量、全量图标名）；`usable: false` 时按 `ui.askUser` 向用户要组件清单。

开工前读一遍项目主规范、`ui-library.md`、全局主题变量文件和目标模块的共享入口（如 `shared.ts`、路由定义）。

**组件卡片**：要用某个组件、但需要知道 prop 默认值、插槽渲染在哪、内部类名或默认样式时，调 `lanhu_dds_doctor({ component: "XwStepper,XwPageContainer" })`。它返回每个组件的 props 类型/默认值/说明、事件、插槽、类名与插槽的出现顺序、全部样式规则体（含 CSS 变量回退值）。这比翻 `node_modules` 里的编译产物快，也不用猜打包后的文件名。定位不到实现的组件会退到类型声明出卡（没有默认值和渲染结构，props、事件、样式规则仍在）。

## 3. 选屏与拍板

`lanhu_dds_screens({ url })` 不落盘、不下载，返回：

- `screens[]`：每屏的 `index`、`title`（导航栏标题）、`texts`（去掉状态栏/导航栏后的全部业务文案）；整屏只有弹层的帧带 `popup: true`（不是每屏都有）。`raster: true` 的屏是整张位图，没有结构，要告诉用户这屏无法结构化还原；`empty: true` 的屏是设计器里的空框（几乎没节点），不要写进 `plan`。
- `pages[]`：哪几屏是同一个页面的不同状态或弹层，如 `{ title: "产品详情", screens: [3, 5], popups: [4, 6] }`。同组的屏对应同一个页面文件。

接着用 `glob` 找到目标业务目录下的页面文件，读各旧页面的 `<script>` 与模板概览，拿 `texts` 对照，列出旧页面里设计稿没画的业务功能（开关、额外表单项、合规提示条）。这一步用 `texts` 就够，不需要先编译。

然后调一次 `ask_user_question`，把下面三件事一起问完（预判的推荐项放第一个并标 `(Recommended)`）。即使用户的原话里已经写了「重构」或「优化」也要问，因为范围和去留仍需确认：

| 问题 | 选择方式 | 选项怎么写 |
|---|---|---|
| 模式 | 单选 | 「整体重构」：丢弃旧模板与旧样式，按设计稿重写，只保留路由/接口/Store 契约。「局部优化」：保留旧骨架，只改设计稿变了的区块 |
| 范围 | 多选 | 每个候选页面文件一个选项，写成「`文件路径` ← 屏 3、4、5、6」。用户原话点名的页面默认勾选；画布里多出来的页面也各列一项，由用户决定。全站公共组件（如 `src/components/` 下的密码键盘）对应的屏不列入，页面里只保留对它的调用 |
| 旧功能去留 | 多选（没扫到就不问） | 每个功能一个选项，勾选 = 保留，不勾 = 按设计稿移除 |

## 4. 编译与产物

把回答原样填进 `plan`：

```js
lanhu_dds_build({
  url,
  plan: {
    mode: "rewrite",                     // 或 "optimize"
    pages: [
      { file: "src/pages/mall/index.vue", screens: [0] },
      { file: "src/pages/mall/detail/index.vue", screens: [3, 4, 5, 6] },
    ],
    keep: ["积存金兑换开关"],             // 用户勾选保留的旧功能
    drop: ["退换货警示条"],               // 未勾选的旧功能
  },
})
```

返回的 `work` 按页面文件分组，每项是该文件名下各屏的规格表与裁图，`variants` 是这个文件里互为状态变体的屏对。它的顺序就是干活的顺序。

`plan` 会写进 `report.md` 顶部和每份规格表的「拍板契约」行。之后任何时候对范围或去留拿不准，以规格表里这一行为准，不需要回忆对话。用户中途改了主意，就用新的 `plan` 再调一次：DDS 与切图有缓存不会重新下载，产物目录会与新 `plan` 保持一致。

产物在返回的 `outDir`（`~/.dsh-lanhu-dds/sessions/<会话>/…`）：

| 文件 | 用途 |
|---|---|
| `screen-N.spec.md` | 主输入。顶部是拍板契约、本屏业务切图与图标清单（尺寸、色值、资源待用户提供）、重复结构候选；正文是带坐标、间距、样式、文案的缩进树 |
| `screen-N.outline.md` / `screen-N.ir.json` / `screen-N.rects.json` / `screen-N.html` | 备查：结构大纲、原始树、几何表、绝对定位预览 HTML。出码用不上，别拿它们替代规格表 |
| `screen-N.png` | 该屏裁图，用 `read_image` 看。图标长相、标 `c:MISSING` 的文字颜色、整体层次以它为准 |
| `variants-diff.md` | 同页多屏之间的差异：各自独有的区块，以及同一元素在两屏里不同的字号、间距、颜色、底色、尺寸、文案。实现多状态页面时按这张表写条件分支，不用自己逐行比两份规格表 |
| `report.md` / `tokens.css` | 拍板契约、编译汇总、高频色值与字体；另有两条提示要看：**未纳入 plan 的屏**（空屏可忽略；整图屏要跟用户确认真要不要；其余补进 plan 或先问用户）、**结构完全一致只有标题不同的屏对**（按一套布局实现） |
| `assets/` | 已下载到本地的切图。要用的图拷进项目静态目录并改成语义化文件名；代码里不引用蓝湖线上 URL |

`img:PLACEHOLDER(尺寸，原因)` 有两种：**切图下载失败**（编译器已依次试过直连、`alipic.lanhuapp.com` 镜像、从原图裁切）和**文字压在背景图上**（图里带着别处的文案，不能直接用）。两种都不用排查网络，按尺寸用 CSS 底色或渐变兜底。

写入项目的只有业务源码、拷入静态目录的图片，以及 `.agents/skills/lanhu-dds-codegen/` 下的接入文件。规格表、JSON、临时脚本留在 `outDir` 或返回的 `tmpDir`；写进项目的会被 `doctor` 报为 `strays`。

## 5. 按模式执行

一次只做 `work` 里的一个文件：读它名下的规格表和裁图，有 `variants` 的再读 `variants-diff.md` 里对应的小节，写完并通过 lint，再读下一个文件的。规格表一直在磁盘上，契约在每份规格表顶部，所以不需要提前通读其他页——先把所有屏读完再动笔的话，规划会反复重做，上下文一压缩还得全部重读。跨页面共用的东西（主题变量、共享组件）在做到第一个用它的文件时定下来，后面的文件沿用。

**文案与数据**：界面上固定的文字（标题、按钮、字段名、提示语）照设计稿。设计稿里的样例数据（商品名、金额、克数、数量、协议名、地址、手机号）只是占位，保持旧代码的数据来源不动：接口字段继续绑定，mock 值和业务协议名不要改成设计稿上的示例。

| | 整体重构 | 局部优化 |
|---|---|---|
| 写法 | `write` 整文件重写模板与样式 | `edit` 定点改目标区块及其样式 |
| 旧源码 | 读一遍，提取五样契约后不再参照：路由入参与跳转、Store/接口取数与字段名、页面级导航与生命周期 Hook、提交校验与弹层联动、公共组件调用点。旧模板层级、旧 class、旧纯视觉子组件不沿用 | 以旧 DOM、class 命名、组件拆分为基准，只对齐规格表里变更节点的尺寸、颜色、文案 |
| 设计稿没画的旧功能 | 按契约的 `保留` / `移除` 执行 | 默认保留，只动用户指定的点 |
| 图片与图标 | 静态图直接用 `assets/` 的新切图覆盖或新增，不用比对它和项目里的旧图是否相同；接口返回的动态图保留原字段 | 没涉及的保持原样 |
| 全站公共组件 | 只保留调用与传参，不改其源码；与设计稿的视觉差异写进交付说明 | 同左 |

## 6. 出码

**冲突时谁说了算**：技术栈、引入路径、路由方式、主题变量名听项目规范；视觉长相听 `screen-N.png`；尺寸、间距、渐变、阴影、圆角听规格表。默认 `unit=design`，数值是 750 设计稿 px，直接写进样式交给构建期换算，不要手动除以 2。

**页面壳层**

- 顶部状态栏和导航栏（规格表里折叠成 `# [顶部导航壳层 默认忽略]`）由宿主提供：标题交给项目的导航机制（如 `useNavigationBar('标题')` 或路由配置），页面从第一个业务节点写起，顶距取它的 `↑nav:<px>`。只有用户明确要自定义沉浸式页头时才在页面里实现。
- 底部手势条（`# [底部安全区占位 …]`）只是安全区示意：吸底栏只还原业务高度，再叠加安全区内边距——优先用项目容器的底栏插槽与防遮挡 Hook（如 `XwPageContainer` 的 `#bottom` + `useFixedBottom`），或 `env(safe-area-inset-bottom)` / 项目的安全区变量。旧页面漏了安全区适配的，重构时补上。没有吸底栏的页面，在滚动容器底部留白并叠加安全区。
- 标 `[完整长图被画布底边截断…]` 的图片用 `width: 100%; height: auto` 按真实比例展示。
- 标 `[空白占位切图，勿渲染]`、`[弹层底层页面预览背景…]` 的节点不输出。

**组件与布局**

- 先查 `ui-library.md` 和模块 `shared.ts`：卡片、按钮、标签、单元格、动作面板、步进器、搜索栏、空态用现成组件。与设计稿差 2–4px 属于组件库的刻度差，用 props、CSS 变量或局部 `:deep()` 调；细节查组件卡片（§2）。
- 规格表「组件候选」列出的重复块抽子组件或用 `v-for`。
- 项目没有内网组件库（`ui-library.md` 里没有可用的）时，按规格表的尺寸与颜色写原生结构，不为了凑组件引入第三方 UI 库。
- `variants-diff.md` 配对的屏合在同一个页面组件里，用响应式状态切换。
- 规格表顶部有「行高 / 派生尺寸 / 内距」三行提示时按它算：文字行高（字号×行高）比图层高大，说明 `↑gap` 是按图层高给的，写了 `line-height` 后要从 margin 里扣掉差额；`jc:space-between` 行里的文本宽与 `←gap` 是实测文字宽的派生量，写死会溢出；多层 `rel()` 没有 `pad:` 时内距要逐层累加。

按规格表的 `col` / `row`、`pad:`、`↑gap` / `←gap` 写 Flex/Grid 文档流；`=parent` 是与父同框的包装层，可合并。`screen-N.html` 是全屏绝对定位的预览，不照搬。标 `[大段留白…]` 的 `↑gap` 是固定高度稿的摆放，用 `flex: 1` / `margin-top: auto` 撑开，别写成固定 `margin`。

**图标**：插件只写图标的 CSS，图标资源由用户提供。这不是待攻克的部分，别在上面花时间。

- 规格表标 `图标占位 … 资源待用户提供` 的节点：按它的尺寸写 `width` / `height`（需要时加 `border-radius`、`background`），单色的把色值写进 `color` 或占位底色，配 `aria-label` 或 `aria-hidden="true"`。
- 不手写 SVG、不去 `node_modules` 或图标库里找“长得像”的、不用 Python/PIL 或 `md5sum` 比对切图、不为图标开浏览器验证。
- `composite-icon:` 是编译器预先拼好的整图，同样只写占位，不引这张图。
- 所有图标占位都是交付待办，`report.md` 的「待用户提供」一节已汇总。

**拿不准就交出去**：插件给不出依据的事（该用哪个图标、某处要不要交互、渐变端点色是否取准），最多自己验证两步就停，写进「未验证项或残留风险」交用户定。开一路调试把它查清，比交出去贵得多。

**编辑**：跑过 `prettier --write` / `eslint --fix` 之后文件内容已变，再 `edit` 前先重新 `read` 要改的片段。

## 7. 验收与交付

1. 对本次改动的文件跑项目规定的格式化与 lint（如 `npx prettier --write <文件>`、`npx eslint --max-warnings=0 <文件>`）。全量生产构建（`taro build` / `vite build`）只在用户要求验证打包产物时跑。
2. 跑一次 `lanhu_dds_doctor({})`（编译时自己指定过 `session` 的话，这里要传同一个 `session`）。它返回 `strays`（应为空）和 `closeout`：本次拍板的页面文件、保留项、移除项。一个会话里编译过多张画布时，`closeout` 是 `{ canvasCount, canvases: [...] }`，每张画布各一组，逐张确认。
3. 对 `closeout` 逐项确认一次：每个文件已实现、保留项还在、移除项已去掉。确认靠写代码时的记忆和 lint 结果，不为此重读已写的文件或规格表；只有想得起某一条具体没做时才回去改。图标占位与资源待提供不算未完成项。
4. 交付，输出：
   - **改了什么**：模式、每个页面文件对应的屏号、复用的组件、保留与移除的旧功能。
   - **怎么验证**：实际跑过的命令与结果。
   - **未验证项或残留风险**：图标占位清单（资源待用户提供）、未纳入的屏、与公共组件的视觉差异；没有就写「无」。

是否提交、提交哪些文件由项目规范决定，本技能不要求提交。项目的 commit hook 报错时修掉报错或把情况告诉用户，不用 `--no-verify` 或改 `core.hooksPath` 跳过。`ui-library.md` 是否入库同样听项目规范；规范没提就保持未跟踪，不和业务改动混在一个提交里。纯视图还原不需要新建决策笔记，除非用户要求。

页面能在本地打开且用户要求 DOM 复核时，可在根元素加 `data-check-root`，在控制台对比 `screen-N.rects.json`（`K = 750 / document.documentElement.clientWidth`，差值 ≤ 3 设计 px 视为通过）。
