# Agent Note: 团队模式第三轮测试——选屏互删崩溃、单帧展示板、规格表读法补齐

Status: implemented

## Problem

第三轮派三个独立验证代理（真实画布选屏回归、出码流程模拟、工具契约对抗测试），前两个报回的问题按严重度排列：

1. **选屏规则互相删空导致崩溃**。机身里放一块比机身更高的滚动内容（`750×1200` 在 `750×900` 里）时，`overflows(机身, 滚动块)` 把滚动块剔掉，`encloses(滚动块, 机身)` 又因为「同宽但更高」的外包关系把机身剔掉，两条规则互补删空 → `best` 为空 → `best[0]` 抛 `Cannot read properties of undefined (reading '0')`。多屏画布上表现为「其余屏静默消失，只返回最后一个」。
2. **单帧展示板仍被当成屏**。展示板灰底做成铺满整板的子矩形时，板自身因为「内容铺满」通过 `contentFill` 判据进了候选，而板里只有一台手机、构不成「≥2 帧并列」，展示板规则不成立 → 板当屏，尺寸 1100×1400。
3. **保留功能在规格表里零信息**。`report.md` 要求保留旧功能（例如「兑换单额外显示积存金抵扣与需补现金」），设计稿里 0 节点 0 文案，而容器是 `446` 定高 + `jc:center`；照抄定高再插两行必然溢出。
4. **行高提示只覆盖单向**。提示只处理「行盒比图层高大」，而标题/多行文案的真实形态是「图层比行盒大」（60 vs 48、84 vs 78.4），照抄 `height` 会和 `line-height` 打架。
5. **「各减一半」有歧义**。两层 `rel(24,24)` 时按字面「各减」得 384，正确是 390——只减紧贴文本行那一层。
6. **`ta` 提示只说一半**。`ta` 在「宽度等于实测文字宽」的节点上是空转（23 个文本节点里 21 个如此），按提示字面会误删真正有效的 2 个。

7. **`screens` 与 `build` 的宽度基准不一致**。同一个屏，`screens` 报画布原始宽（1404）、`build` 报按项目 `designWidth` 归一后的宽（750），返回里还没有 `unit` 可自证；`screens` 工具从来没读项目配置。
8. **两类错误提示把人引向链接和 Cookie**：`build` 缺 `url` 时沿用「检查 image_id / Cookie」的提示；响应体非 JSON 时的文案不匹配网络正则，也落到同一条提示。

## Decision

- 选屏管线排序改为：**先剔溢出内容，再做同矩形取帧，再做包含去重**。两条「剔除」规则不再同时作用于同一对节点，互补删空的可能消失。
- 抽出 `rootFallback()`，在「无候选」「`best` 为空」两处兜底：宁可产出「整块画布当一屏」的规格表（会在规格表顶部标明），也不能返回空屏或抛错。
- 展示板门槛从「内部帧宽度 ≥ 自身 80%」放宽到 50%（真实画布上屏里的内容块只有 335/750 = 0.45，仍然安全），并新增一层**单帧展示板**兜底：若某个候选内部只有一台页面帧（面积比 < 0.7）、帧外还有别的直接子节点（标题牌/图注），就换成那台手机。
- 规格表补两条提示（都是「照抄必错」的那类）：`文字盒高度提示`（图层高 > 行盒时按行盒写 `line-height`，多出来用上下 `padding` 各补一半）；容器尺寸提示补「含 `jc:center` 的行容器」「往定高容器里补内容会溢出」。
- 行高提示的「各减一半」限定为「只把紧贴文本行那一层，外层容器内距不要再减」。
- `ta` 提示补「只在盒子明显宽于文字时才有意义，宽度等于文字宽时是空转」。
- `lanhu_dds_screens` 也读项目 `designWidth`（与 `build` 同一个基准），返回里补 `unit` 与 `div`/`designWidth`，两个工具的数字不再差倍数。
- `describeError` 里「缺少 url」单独一支，给出「把设计图链接整条传进来」的可执行提示、且不再提 Cookie；网络分支正则补 `非 JSON`。
- `report.md` 在保留项非空时加一行，说明保留项在设计稿里通常没有结构，且容器不要照抄固定 `height`。

## Alternatives considered

- **把 `overflows` 与 `encloses` 合成一个函数**：两个判据方向相反（一个判「内容比机身长」，一个判「容器包住子块」），合并后需要在函数内部分支，反而更难验证；分阶段顺序执行更直观。
- **选屏失败直接抛错**：会让模型自己找原因（0.9.0 爆栈那次的教训），不如产出可用的降级结果并在规格表里说明。
- **靠 `isFrame` 整体过滤候选**：试过，gold 从 10 屏变 18 屏——真实画布的屏是 `lanhubox`，里面的内容帧才是 `lanhupage`，整体筛会反过来把内容帧当屏。只能用于「同一矩形」的两个候选分高下。
- **展示板门槛继续用 80%**：单帧展示板（750 手机在 1100 板上 = 0.68）会被漏掉，且 0.45 的真实内容块会误伤，所以必须放宽并另加「帧外还有东西」这一条。
- **行高提示只给通式不给例子**：验证代理明确说例子（`↑gap:35、line-height 34、图层高 28 → margin 29`）才是他一次算对的原因，去掉反而更差。

## Consequences

- 选屏：`single / multi / board / stack` 四种合成场景全部选对；5 张真实画布 result 1 / invoice 4 / address 8 / orders 5 / gold 10 屏、宽度集合全 `[750]`、scale 全 2。
- 规格表：`文字盒高度提示` 在支付结果页命中 2 处，容器尺寸提示带上「补内容会溢出」；行高提示例子不再给负 margin。
- 已知仍不准：一帧被单独塞进比它宽得多的行容器分组时只选到其中一帧；展示板上除那台手机什么都没有时仍会当屏。两条都写进 `README.md` 已知边界。
- 验证：`verify-091` / `verify-092` 全 PASS；`team/b` 六套件 54/56、54/54、21/22、25/25、6/6、27/28；`team2/b` 八套件 175/175、24/24、15/15、69/69、17/17、23/23、19/19、28/32（剩余 4 条是「与 0.9.3 对照」的过期断言与上述已知限制）。
- 代价：选屏多了一次 `cands` 级的三次遍历（候选量级是十位数，可忽略）；规格表多两行提示，每屏约 200 字节。
